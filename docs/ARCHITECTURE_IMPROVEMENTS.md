# Улучшение архитектуры HMI

## Текущие проблемы

1. **MainWindow знает слишком много** — вручную задаёт имена, адреса, типы и вызывает `addVar` для каждого виджета. Добавление переменной = правки в нескольких местах.

2. **Привязки размазаны** — имя в `setName()`, адрес в `addVar()`, тип/формат в отдельных вызовах. Нет единого описания «что с чем связано».

3. **ModbusManager жёстко зависит от ModbusModel** — вызывает `variableCount()`, `variableAt()`, `findVariable()`, `updateVariable()`. Сложно тестировать и подменять источник данных.

4. **Дублирование настроек** — при смене настроек Modbus MainWindow вызывает три метода (`setUnitId`, `setPollIntervalMs`, `connectTo`). Логичнее один вызов `applySettings(ModbusSettings)`.

---

## Рекомендуемые улучшения (по приоритету)

### 1. Конфиг привязок (высокий приоритет)

**Идея:** один источник правды: имя переменной → адрес (и при необходимости размер).

**Вариант A — структура в коде (мини-рефакторинг):**
- Ввести `struct VariableBinding { QString name; quint16 address; }` и массив/вектор привязок.
- В MainWindow: один цикл «по привязкам + findChild по имени или по property» и вызов `model->addVar(variable, binding.address)`.
- Имена виджетов или property задаются в UI/конфиге, адреса — в одном месте.

**Вариант B — конфиг (QSettings/JSON):**
- Секция вида `[modbus/bindings]`: `Temp=100`, `Counter=102`.
- При старте: загрузка конфига, поиск виджетов с `property("modbusVarName")` и регистрация в модели по конфигу.

**Результат:** добавление переменной = одна запись в конфиге или в массиве привязок, без правок логики MainWindow.

---

### 2. ModbusManager::applySettings(ModbusSettings) (высокий приоритет)

**Идея:** при смене настроек Modbus вызывать один метод вместо нескольких.

- В `modbusmanager.h`: объявить `void applySettings(const ModbusSettings &settings);` (нужен include или forward declaration `ModbusSettings`).
- В реализации: `setUnitId(settings.unitId)`, `setPollIntervalMs(settings.pollIntervalMs)`, `connectTo(settings.ip, settings.port)`.
- MainWindow и диалог вызывают только `manager->applySettings(newSettings)` после сохранения в QSettings.

**Результат:** меньше дублирования, одна точка входа для смены конфигурации Modbus.

---

### 3. Интерфейс «репозиторий переменных» (средний приоритет)

**Идея:** ModbusManager не зависит от класса ModbusModel, а от абстракции.

- Ввести интерфейс, например:
  - `int variableCount() const;`
  - `ModbusVar *variableAt(int i) const;`
  - `ModbusVar *findVariable(const QString &name) const;`
  - `void updateVariable(const QString &name, const QVector<uint16_t> &data);`
- ModbusModel реализует этот интерфейс.
- ModbusManager принимает указатель на интерфейс и только его использует.

**Результат:** тестирование с mock-моделью, возможность подставить другую реализацию (прокси, кэш и т.д.) без изменения менеджера.

---

### 4. Описание переменных в данных (средний приоритет)

**Идея:** тип, формат, лимиты (min/max, дробные знаки) не задавать в коде для каждого виджета, а хранить в конфиге или в модели.

- Расширить конфиг привязок (или отдельную таблицу): имя, адрес, размер, тип (Word/DWord), формат (int/float/hex), min, max, fractional.
- При инициализации создавать/настраивать `Variable` по этому описанию (или фабрика виджетов по конфигу).

**Результат:** масштабирование без правок кода при добавлении новых переменных.

---

### 5. Слой приложения / композиция (низкий приоритет)

**Идея:** при появлении нескольких экранов или сервисов вынести создание и связывание в отдельный слой.

- Класс вида `HmiApplication` или `ApplicationController`: владеет настройками, конфигом привязок, создаёт ModbusModel и ModbusManager, применяет настройки.
- MainWindow получает уже настроенные model и manager (через конструктор или геттеры) и только подключает сигналы к UI.

**Результат:** MainWindow занимается только отображением и реакцией на действия пользователя; композиция и конфигурация — в одном месте.

---

## Порядок внедрения

1. **applySettings** — быстрый рефакторинг, сразу уменьшает дублирование в MainWindow и в обработчике диалога настроек.
2. **Конфиг привязок** (структура в коде) — убирает хардкод имён и адресов из конструктора MainWindow.
3. **Интерфейс репозитория** — при необходимости тестов и гибкой подмены модели.
4. **Описание переменных в конфиге** — при росте числа переменных.
5. **Слой приложения** — при усложнении приложения (несколько окон, сервисы).
